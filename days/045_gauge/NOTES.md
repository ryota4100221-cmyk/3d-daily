## 新しく入れた技法

### 1. フェッチの**面積**を、選ぶのをやめて測る（`src/footprint.js` / `ltc.js`）

Day 041〜044 の足跡の大きさは、**誰も測っていない2つの定数**で決まっていた。

- `delta = 0.5 rad` — Day 041 が近景の板を見ながら目で決めた角半径。
- `SUPPORT = N/√3` — Day 044 の支持域。**単位正方形**の共分散 `(1/12)I`。

どちらも「この開口は6枚のペインが3段で、間に石がある」ことを知らない。

しかし**カーネルには面積があり、面積は選ぶものではない**。uv で書くと

```
k(u,v) = max(w_z, 0) · j(u,v),      j = dω/dA_uv
```

——ローブの密度 × 窓の平面から球面への変数変換。この k について、`glassFetch` が
そこに到達した時点で**すでにスタックに乗っている事実が2つある**：

- **質量。** `W = ∫k = π·ltcClip(f)`。これは新しい主張ではなく、**LTC 法自身の
  主張**——呼び出し側がこの tint に掛けようとしているスカラーそのもの。しかも
  `ltcVector` は**ペイン単位**で、各ペインの可視率 `vis[i]` で重み付けて、地平線で
  クリップして合計している。**桟も3段も遮蔽物の縁も、全部もう中に入っている。**
- **ピーク。** `p = w.z · |det J|`、そして `|det J| = √(lmin·lmax)` ——楕円の
  *形* をさっき作った固有値2つ。掛け算1回。

**質量 ÷ ピークは面積である。** 楕円上で一様なカーネルならちょうど `π·a·b`、同じ
共分散のガウスならその半分。だから無次元の**プロファイル定数1つ**が差を運ぶ：

```
a·b = κ · ltcClip(f) · N² / (w.z · √(lmin·lmax))
```

**delta はどこにもない。** 形（アスペクトと向き）は今まで通り Q から。今日は
**大きさだけ**を幾何から放射計測へ移した。極限も両方クランプ無しで正しい：開口より
ずっと細いローブは p が大きく面積が小さく、開口を覆うローブは W も p も開口自身の
値に寄るので楕円は窓へ収束する。

実装は `semiA *= gain; semiB *= gain;` の2行で、**アスペクトは一切触らない**。
だから `uMass = 0`（`?mass=0` / `m` キー）は Day 044 とテクセル単位で同一。

### 2. 参照を「囲み矩形」から「6枚のペイン」へ（`scripts/lobe-error.mjs`）

昨日のハーネスは**囲み矩形**の上で積分していた——石も含めて。フェッチが読む矩形が
それだから、という理由で。だが因数分解されている積分の定義域は**光源**であって、
光源は3段6開口である。`ltcVector` が和を取る領域がそれで、返すスカラーはその領域の
質量なのだから、**正しい tint は「ペインの上の D 重み付き平均」**でしかありえない。

昨日は「参照の**重み**が間違っていた」を直した。今日は「参照の**定義域**が
間違っていた」だった。`--domain=square` で昨日の参照が復活し、両方を印字する。

### (a) 参照を動かすと、全員が同じだけ悪くなる

```
  参照＝囲み矩形（Day 044）      Day041  Day042  Day043  Day044  Day045
  全体                            8.48    8.33    8.09    4.44    4.42

  参照＝6枚のペイン（今日）
  窓の1/10                       14.11    7.24    7.81    8.53    3.55      10
  1/10〜1/2                       7.31   11.83   10.09    4.74    4.50      41
  窓と同程度                       9.04   13.99   12.73    6.00    5.47     106
  数倍広い                         9.35   10.67   10.66    6.20    5.59     292
  一桁広い                        11.37    8.86    8.86    6.25    6.02     575

  全体                           10.49   10.14    9.90    6.18    5.77    1024
```

読み方が3つある。

1. **移設の監査は通った。** 上段の4つ（8.48 / 8.33 / 8.09 / 4.44）は Day 044 の
   NOTES の表と**印字された桁まで、5つのビン行すべてで一致**する。参照を切り替え
   られるようにした改造は、昨日の答えを一つも動かしていない。
2. **参照を動かすと 4.44 → 6.18。1.74 ポイント。** これは Day 042 と Day 043 の
   改善を合計した 0.39 の**4倍以上**である。原因は一行で言える——**フェッチは桟を
   平均しているが、積分は桟を見ていない。** ピラミッドは石の描かれた画像の上に
   立っていて、窓の 29% は石である。
3. **今日の 6.18 → 5.77 は、その上での 6.6% 削減。** そして昨日の参照の上では
   4.44 → 4.42 で**引き分け**である。これは失敗ではなく、むしろ整合している：
   矩形の開口に対しては Day 044 の「単位正方形」という仮定が**厳密に正しい**。

### (b) κ は 1.2。プロファイルとして正しい範囲に入った

```
     kappa    RMS %   厳密な質量   平均タップ   A / 測定された A
      0.60     7.64       7.74       1.36        0.646
      0.80     6.59       6.68       1.36        0.746
      1.00     5.97       6.02       1.36        0.834
      1.20     5.77       5.75       1.36        0.914   <- 今日
      1.50     5.93       5.86       1.36        1.022
      2.00     6.37       6.27       1.36        1.179
      3.00     7.30       7.17       1.36        1.444
```

- 最小は **κ = 1.2**。1（楕円上で一様）と 2（同共分散のガウス）の**間で、平坦側に
  寄っている**——開口で切り落とされた余弦、という形に対して符号が正しい。もし
  この区間の外に落ちていたら、質量÷ピークという恒等式にプロファイルでない誤差を
  吸わせている証拠になるので、**どこに落ちるか自体が今日の検算**だった。
- **地平線フィットの代金は 0.02 ポイント**（5.77 対 5.75）。質量そのものの誤差は
  `π·ltcClip(f)` 対 厳密値で **平均 1.043 倍・RMS 11.24%** もあるのに、である。
  理由は2つ：面積から半軸へは**平方根**で入り、ripmap の索引は **log2** である。
  11% の質量誤差は半軸で 5.5%、レベルで 0.08 段にしかならない。

### (c) 第二モーメントを合わせることは、誤差を最小にすることではない

```
                    major    minor
  Day 043          98.332   18.379
  Day 044 + 支持域   0.978    1.000
  Day 045            0.914    0.907
```

**Day 044 の楕円は、測定された共分散に 2% で一致している。** それでも 6.18 で、
9% 小さい今日の楕円が 5.77 である。κ を 1.5 にすれば共分散はぴったり合う（1.022）が
スコアは 5.93 に悪化する。**この2つが分離できたのは今朝が初めて**で、以後
「共分散が合った」は結論ではなく手がかりとして扱う。理由は推測できる——参照の裾は
石で、ぼかし過ぎは石を引き込み、絞り過ぎは引き込まない。非対称なのだから最適は
中心にない。

### (d) 開口の「形」は、その充填率を超えては、ほとんど払わない

これが今日いちばん確かめたかったことで、答えは**ほぼノー**だった。κ を両方自由に
して、質量をペインから取る場合と囲み矩形から取る場合を並べた：

```
     kappa    panes    rectangle
      0.80     6.59         5.83
      1.00     5.97         5.86
      1.20     5.77         6.05
      1.30     5.80         6.16
```

**ペイン 5.77（κ=1.2）対 矩形 5.83（κ=0.8）。0.06 ポイント。** 2つの最小値の κ の
比 1.5 は、ペインが矩形の 71% を覆うことのほぼ逆数で、つまり**開口の形は主に
「充填率」という1つの数として入り、κ がそれを黙って吸ってしまう。**

それでもペインの質量を使う。理由は2つあり、どちらも harness には見えない：
`ltcClip(f)` は**すでに計算済み**なので矩形の質量を別に作る方が高い。そして
ペインの質量は**各ペインの可視率を運んでいる**——半影の中では窓の一部だけが隠れ、
矩形の質量はそれを言えない。**ハーネスには遮蔽物が1つも無いので、この差は今日の
表のどこにも出ていない。** 出ていないことをここに書いておく。

## つまずき（記録用）

**κ を 1.55 で書き始めて、掃引で否定された。** 「クランプ余弦は一様よりガウス寄り
だろう」と当たりを付けて 1.55 を既定値にし、ハーネスを回したら**κ が小さいほど
良い**という単調な列が出た。原因は今日の推定が使う「ピーク」が**カーネルの最大値
ではなく、フェッチ点（ローブの平均方向）の密度**だから——平均方向は最頻方向より
密度が低く、質量÷それは面積を過大評価する。κ はその分も吸っている。
**「導出から出た定数」と「測った定数」は別物**、という Day 044 と同じ教訓を、
今度は自分の当たりを付けた側で踏んだ。

**`?pass=18` を先に `MODE_GAIN = 18` と書いてしまった。** モード番号は 0 起点で
`?pass` は 1 起点なので、正しくは 17。`?pass=18` が何も出ずに合成が出る、という
静かな失敗で、`App.jsx` の上限（`PASSES.length + 7`）も合わせて 1 上げた。番号が
2箇所にある形は Day 042 が一度払っている。

**参照を動かす日は、旧参照が再現することを先に確かめる。** `--domain=square` で
1024 構成を回して Day 044 の表と全桁一致させてから、ペイン側の数字を1つも読まな
かった。もし一致していなければ「参照を動かしたから悪くなった」と「改造でどこかを
壊したから悪くなった」が**区別できず、しかもそれは結果に見える**。Day 044 が
`rip.mjs` を切り出したときと同じ手順を、同じ理由で。
