# Day 039 — Loop 12 · 遮蔽が光源を編集する「Eclipse」（shadowed area light / ペイン単位の可視性マスク）★★★★★

## 狙い

Day 038 の NOTES は「次に試したいこと」の一番上にこう書いた：

> **影のある面積光源（shadowed area light）**。今日も `vis`（窓のうち見えている
> 割合・スカラ）と「全部見えている前提の積分」を掛けている。遮蔽物が窓の
> 片方の灯だけを覆っているときの正解は**見えているペインだけの積分**。

今日それをやった。そして実装してみると、これは新しい数学を必要としない
**削除**の日だった。増えた行より消えた行のほうが主張が大きい。

昨日までのシェーディングはこう書かれていた：

```glsl
return uLightCol * (uSrcRad * vis) * (albedo * ffD + ffS);
```

この `vis` が最後の嘘だった。**スカラを掛けるという行為は「窓が暗くなった」と
主張している**。実際には窓は暗くなっていない。梁は開口の一部を覆い、残りは
1ルクスも失っていない。だから今日の1行はこうなる：

```glsl
return uLightCol * uSrcRad * (albedo * ffD + ffS);   // vis が消えた
```

`vis` はどこへ行ったか。**積分の中**へ、ペインごとの重みとして入った。

## 新しく入れた技法

### 1. 可視性がスカラをやめてマスクになった（`shadow.js`）

昨日の `softVisS` は24本のタップを打ち、当たった数を割って返す。だが
**タップはどのペインを撃ったか知っていた**——足して割る、その最後の1行までは。

だからループを裏返した。外側をペイン、内側をそのペイン自身のタップにする：

```
for pane i:
    for tap j in tp:            tp = SH_PCF / paneN
        visP[i] += step(...)
    vis += visP[i] * (ペインiの面積比)   ← CDFの差分がそのまま面積比
```

返るのは**ベクトル**（`visP[i]` = ペイン i の見えている割合）で、スカラは
面積加重平均として同時に返す。空気（froxel）と塵（motes）は1つの数しか
要らないので、彼らの呼ぶ `softVis` は1行も変わっていない。

**タップ配分も変わった。**昨日はCDFで面積比例に配っていた——それは*平均*の
ための重点サンプリングであって、*ペインごとの推定*には間違った配分。各ペインの
割合は各ペイン自身の問いなので、**等分**が正しい。光源が1枚の矩形になる比較
モードでは、その1枚が全タップを受け取り、昨日と完全に同じものになる。

### 2. マスクをLTC積分の中に入れる（`ltc.js`）

これが今日の主張で、そして**新しい数学は要らない**：

> 辺の和はまだ形状係数ではなく**ベクトル**（立体角上の方向の積分）であり、
> ベクトル積分は領域の分割について加法的である。**加法性は、断片に重みが
> ついていても気にしない。**

だから `sum += (4辺) * visP[i]` と書けば、それは「放射輝度 × 可視性」の積分
そのもの——可視性をペイン上で区分定数に保った近似での。Day 038 が「6枚のペインが
1枚と同じ値段」であることの根拠に使った性質が、そのまま「影つき面積光源」の
根拠になる。**同じ1文が2日分を支えた。**

拡散項も鏡面項も同じ配列を受け取る。窓が半分欠ければ、ハイライトも
ターミネータも同じように半分欠ける。

### 3. デコリレーションが2次元になった（`passes.js`）

Day 038 は「回転ではなく平行移動（Cranley–Patterson）」に正しく直した。だが
**その2成分を1つのスカラから作っていた**：

```glsl
off = fract(vec2(rot * 0.1591549, rot * 0.2756644));
```

1つの数の線形関数を2つ並べても正方形は埋まらない。数本の平行線をなぞるだけだ。
つまり**隣接ピクセルは同じ方向にずれたサンプル集合を渡されていた**。答えが
1つの数のうちは誤差が平均で相殺されるので見えない。答えがマスクになった瞬間、
**全ペインの推定が一斉に同じ方向へ動く**——タブレットの食の縁に細い縞が出る。
最初これをペイン量子化のせいだと思って20分溶かした。

直し方：ピクセルごとに**独立な2つのハッシュ**（`ign` と `hash12`）、フレーム
進行はR2列の2つの無理数で。縞は消えた。

### 4. 梁（`rig.js`）——軸は選ぶものではなく導くもの

新しいオブジェクトは1つだけで、これも一度も映らない（Day 031 からの規則）。
どの軸に沿って走らせるかは、次の連鎖で決まっていて選択の余地がない：

```
プレートはビームに正対 → local x = 光源フレームのx / local y = 同y
WINDOW.axis が90度回す  → 光x = 窓の「高さ」（中連子が割る）
                          光y = 窓の「幅」  （方立が割る）
```

既存のスロットは縁が local x にあるので、半影は窓の**高さ**方向に掃かれる
（受光面は段＝tier を順に失う）＝Day 038 の絵。今日の梁は縁が local **y** に
あるので、半影は窓の**幅**方向に掃かれ、受光面は**片方の灯（3ペイン）を丸ごと
失う**。方立があるおかげでそれが「グラデーション」ではなく「欠け」として読める。
**石が無ければ、欠けは減光と見分けがつかない。**

位置は打ち込まず**解く**：`screen.worldToLocal(tabletA.position).y` にオフセット。
光は正射影なので、プレート local (x,y) の特徴はどれだけ下流でも同じ (x,y) を
覆う——探索ではなく射影で済む。`?bar=0.45` でビルドせずに動かせる（半影幅が
1.35mある画面で、食の位置は数cmの勝負なので）。

## つまずき（記録用）

**またバッククォートを踏んだ。**Day 038 の NOTES が「シェーダ文字列内の
コメントでバッククォートを使うな」と大文字で書いていて、それでも3回踏んだ
（`` `vis` ``、`` `sofs` ``、`` `off = fract(...)` ``）。ビルドエラーは
`/* glsl */ \`` の中の行を指すので発見自体は速いが、**警告を書いた本人が
翌日に3回踏む**なら、警告ではなくlintで止めるべきという話。次にこの系列を
触るときの最優先。

**タップ数を24→48に増やした。これは正直に言う必要がある。**マスク自体は
無料だ——同じループの割り算を移しただけで、テクスチャ読みは1回も増えていない。
だが**推定量の分散は6倍**になる。1ペインの背後に立つサンプルが1/6になるからだ。
ハイライトの上ではトーンマップが飽和していて 0.75 も 1.0 も同じ白なので誰も
気づかない。**食の縁**、ペインが 0.25 に座るところでは全員が気づく。
「マスクを*使う*コスト」はゼロ、「マスクを*推定する*コスト」は倍。

**食が深すぎた（最初の版）。**梁を tablet の中心の 0.16m 手前に置いたら、窓の
像の8割が消えて「窓が欠けた」ではなく「板に影が落ちた」になった。加えて 2.4m の
帯が page の手前左角を丸ごと飲み込み、画面が夜になった。`?bar` を足して
-0.16 / 0.30 / 0.45 / 0.70 を撮り比べ、**0.45**を採用——十字の腕が残ったまま
左下の1/4が食われる。残りが「窓の断片」として読める最小の残し方。

**梁は半平面ではなく帯にした。**6mの梁は court の手前を全部影にする。2.4mなら
自分の半影の底で1m弱の縞を投げて、タブレットを横切って、奥は明るいままでいる。

**`?pass=8`（マスクを平坦化）が想像以上に強い比較になった。**予想は「窓が
半分の明るさで全部見える」だったが、実際は**食が完全に消える**。飽和した
ハイライトは半分にされても飽和したままだからだ。つまりこの絵において、
昨日までのシェーディングは遮蔽を**なかったことにしていた**。15%の誤差ではなく、
出来事そのものの欠落。

## 構図・トーン

- 光は1つ。フィルもアンビエントも環境マップも無い（Day 036 から継続）。
- **主役は手前の漆板**。同じ窓・同じランプで、昨日は十字が全部あり、今日は
  左下が食われている。奥の板は梁の影の外にいるので**昨日の窓を丸ごと持っている**
  ——粗さで閉じたロゼンジとして。1枚の絵の中に「遮蔽あり」と「遮蔽なし」が
  同時にある。
- 釉薬の玉・鉢・梁と柱の裏（直接光が厳密にゼロ）はすべて Day 034/035 の在庫
  確認として据え置き。
- Day 031 からの規則——**作品が中心に据えている物体（窓・絞り板・今日の梁）は
  一度も映らない**——を継続。

## 次に試したいこと

- **ペインの細分割**。マスクの解像度は今日「石のあるところ」＝トレーサリー
  そのもの。遮蔽の縁がペインの内側に落ちると、そのペインは一様に減光する
  ——局所的に昨日の誤りに戻る。各ペインを幅方向に2〜4分割すれば解像度は
  上がるが、辺は分割数に比例するので LTC のコストが直接増える。まず
  「鏡面だけ細かく、拡散は粗く」を試すべき。
- **ltcClip が重み付き和を受け取っている**。Heitz の地平線フィットは一様に
  明るい多角形のために導かれたもので、部分遮蔽された多角形は訓練の外側。
  この画では全部の受光面が窓を正面から見ているので見えないが、グレージング角の
  床では見えるはず。ペインごとにクリップすると二重補正になる（Day 038）ので、
  正しい直し方はまだ分かっていない。
- **froxel にもマスクを**。空気は今日も HG 位相関数×スカラ可視性。シャフトの
  断面がトレーサリーになるはず（Day 038 からの持ち越し）。240万セルに配列を
  持たせるコストが問題なので、たぶん SH 2次あたりへの投影が答え。
- **窓を透過体にする**（Day 038 からの持ち越し）。すりガラスは「面積光源そのものが
  等方でない」＝方向で輝度が違う光源で、LTC はそこまで持たない。
- **froxel への影のキャッシュ**（Day 036 からの持ち越し）。
- **シェーダ文字列のバッククォートをlintで止める**。3日連続で踏んでいる。
