## 新しく入れた技法

### 1. 本物の ground truth（`scripts/lobe-error.mjs`）

LTC 変換をかけた後、シェーディング積分は「多角形の上のクランプ余弦」である：

```
I = ∫_P L(ω) D(ω) dω,      D(ω) = max(ω_z, 0) / π
```

手法の全体は、これを (スカラー) × (色) に分解することだった。スカラーは LTC の
辺積分で、これは厳密で、既に計算済みで、議論の対象ではない。色は

```
tint = ∫ L D dω / ∫ D dω          窓の画像の、D で重み付けた平均
```

**これは総当たりで計算できる。** それをやるのが今日のハーネス。旧参照と3点で違う：

1. **重みがある。** ローブは中心が重く、地平線でゼロになる。旧参照は楕円の中を
   全部同じ重さで数えていた。
2. **delta が入っていない。** 広がりを決めるのは多角形とローブ、つまり幾何であって、
   「delta はいくつであるべきか」は選択ではなく**測定**になる。
3. **開口でクリップされる。** `[0,1]²` の外に平均すべきものは無い。窓より広い
   カーネルは**窓そのもの**であって、窓の一部をクランプして読んだものではない。

全部**変換後の空間**でやる。そこではローブは構成上クランプ余弦で、光源は一般の
平行四辺形——`glassFetch` が既に働いている空間そのものなので、**1つのハーネスで
両方のローブを覆う**。拡散側は恒等変換、2枚の漆板は同じコードで多角形が LTC 行列に
引き伸ばされただけ。

### 2. 窓はカーネルの半分である（`ltc.js` / `footprint.js`）

測ってみると、シェーダが要求する楕円は**測定されたカーネルの長軸の平均105倍**
だった。理由は一行で言える。**delta = 0.5 rad の円板は、この窓（13°×21°、
0.23 × 0.36 rad）より初めから大きい。** だから拡散面のフェッチは常にピラミッドの
天辺——窓全体のフラット平均——を読んでいて、ローブの形は捨てられていた。

シェーダは3日間これを「uv を [0,1] にクランプする」という形で言い続けていた。
**しかしクランプはフェッチの中心を動かすだけで、大きさを縮めない。**

直し方は 2 行：カーネルが 2 つの積なら、**分散は逆数で足し合わさる**。しかも
単位正方形の共分散は厳密に等方の `(1/12) I` なので、支持域の項は**楕円を回さず、
両軸を短くするだけ**——固有ベクトルは昨日のままでいい。半軸 a を正方形の分散に
合わせると a²/4 = N²/12 なので、正方形は半軸 `N/√3 = 147.8` texel の楕円と同じ重さ：

```
1 / A_eff² = 1 / A² + 1 / SUPPORT²
```

`uSupport = 0` は Day 043 **そのもの**。`?supp=0` が昨日、`?supp=0&tap=1` が
Day 042、`?supp=0&aniso=0` が Day 041——**1つのアトラスの上に4つのビルド**が乗り、
17個のパスのどれからでも見られる。

### 3. `?pass=17` — 今日が効いている画素の地図

赤 = 窓の支持域が長半軸から削った割合、緑 = 短半軸から削った割合。

- **黒** = ローブが開口の中に収まっている。フェッチは昨日と texel 単位で同一。
- **黄** = 両軸とも消えた。楕円は絵より大きく育っていて、フェッチは黙って
  窓全体のフラット平均になっていた。**8.09% はここにあった。**
- **赤** = 長軸だけがクリップされた。斜めに見た面で、桟を横切っては解像するが
  桟に沿っては走り抜けてしまうローブ。

石は一面の黄、近景の板は中央が黒く縁が赤い。**これは Day 043 の `?pass=16` の
ほぼ反転画像**で、それが今日の位置を一番よく言っている。昨日が効いていたのは
黒い画素で、今日が効くのは黄色い画素で、黄色い画素の方が圧倒的に多い。

## 測ってわかったこと

厳密なローブ重み平均に対する相対 RMS 誤差、%。1024 構成、384×384 グリッド。
構成は作品の実寸から生成（開口 13°×21°・距離24・法線は開口が見える半球全体・
LTC の伸長は 1〜256 倍を対数一様）。

```
  フットプリント        Day 041   Day 042   Day 043   Day 044   +中心も
  窓の1/10               12.03      7.47      6.42      7.04     8.43     10
  1/10〜1/2               7.12     10.81      9.32      3.37     5.53     39
  窓と同程度              7.36     12.47     11.34      4.37     7.83    103
  数倍広い                7.34      8.74      8.73      4.44     7.62    294
  一桁広い                9.19      6.90      6.90      4.46     6.80    578

  全体                    8.48      8.33      8.09      4.44     7.13   1024
```

読み方が4つある。

1. **8.09 → 4.44。誤差はほぼ半分。** 過去2日の改善（8.48 → 8.33 → 8.09）を
   合計しても 0.39 ポイントで、今日は 3.65 ポイント。3日ぶんの改良より、
   最初のモデルが間違っていた分の方が大きかった。
2. **Day 042 と 043 は、この参照では Day 041 に負ける帯がある**（窓の 1/10〜同程度で
   10.81・11.34 対 7.12・7.36）。異方フィルタは楕円を**正しく**読むほど、窓より
   大きい楕円を正しく読んでしまう。等方の Day 041 は log2(√AB) を読むぶん実効的に
   小さく、偶然そこで救われていた。**「昨日より良い」は「近似している対象が
   正しい」ときにだけ意味がある。**
3. **今日は昨日を安くする。** 平均タップ数 3.47 → **1.35**。楕円が短くなれば
   異方比が下がり、選ばれるタップも減る。Day 043 の予算はそのままで、支払いが
   61% 減った。
4. **タップはまだ効くが、効き幅は縮んだ。** n≤1 で 4.51、n≤4 で 4.44。旧参照では
   タップは 7% の改善だったのが、厳密なローブに対しては 1.6%。理由も表に出ていて、
   **測定されたカーネルの異方比は平均 1.44 倍しかない**——開口が切り落とすので、
   ローブの楕円が言うほど細長くならない。

### delta を初めて測った

```
     GLASS_K   delta      Day 043   + support   mean taps
        48     0.188        7.50       4.84       1.64
        64     0.250        7.66       4.65       1.53
        96     0.375        7.92       4.49       1.41
       128     0.500        8.09       4.44       1.35   <- 今日
       160     0.625        8.21       4.44       1.32
       192     0.750        8.30       4.46       1.29
       256     1.000        8.40       4.50       1.25
       448     1.750        8.61       4.64       1.16
```

- **Day 041 が目で決めた 128 は、支持域さえ入っていれば測定上の最適とほぼ一致する**
  （128 と 160 が同値、96 と 192 で +0.02〜0.05）。目は正しかった。
- **支持域が無いと、同じ掃引は与えた中で一番小さい delta を欲しがる**（48 で最良）。
  楕円が絵からはみ出すのを止める手段が delta を縮めることしか無いからで、
  つまり**Day 041〜043 の delta は、2つの仕事を1つの数で兼ねていた。**

### 同じ導出の後半は、測ったら損だった

ガウス同士の積は分散を縮めるだけでなく**平均も動かす**。同じ式から中心を窓の中央へ
引く項が出るので、当然入れて測った：**4.44 → 7.13 の悪化**。入れなかった。

理由も測定で言える。支持域は**ガウスではなく箱**で、箱を掛けるのは truncation
であって shift ではない。同じ分散のガウスが平均を動かす量に対して、切り落としが
動かす量ははるかに小さい。**「同じ導出から出た2項だから両方入る」は成り立たない。**
`?supp=0` と同じ形で片方だけ残した。

### レンダ上では「大きいが静か」——そしてその理由は自分で書いてあった

`?pass=2`（積分だけ）を固定 `SHOT_BUDGET` で撮って `tap-diff.mjs`：

| | mean \|dL\| | ≥1 levelの画素 | 隣接相関 |
|---|---|---|---|
| **既定 対 `?supp=0`**（今日の差） | 0.130 | 4.00% | **0.406** |
| **同じビルドを2回**（床） | 0.534 | 10.28% | **0.283** |

**指標では倍近い改善なのに、フレーム上は Day 043 の差（0.377）より静かである。**
理由は `glass.js` に3日前から書いてあった：**ピラミッドの平均は白に正規化してある**
（「色と量は分離できるので、ガラスを灰色にすることは露出変更ではない」）。
だから「窓全体のフラット平均」と「窓全体の余弦重み平均」は**平均が構成上一致し、
食い違うのは窓自身の勾配のぶんだけ**——左灯が古く暖かく、右が冷たく緑がかり、
敷居へ向かって深くなる、あの勾配だけ。片側に強い勾配を持つ窓なら、同じ修正は
はるかに大きく出る。**この窓に限って小さい。**

そして `diff-supp.png` は `?pass=17` の黄色い領域と一致する：**差は照らされた石の上
にだけあり、板の上には無い。** 大きさでは床（時間ノイズ）の 1/4 だが、相関 0.406 対
0.283 で**斑点ではなく絵**——Day 043 で立てた「順位は付けられないが場所は言える」を
今日も同じ形で使った。順位は CPU 側にある。

### 重みのプロファイルは、まだ関係ない

スラブの重みを一様円板の弦（`area`）からガウス（`gauss`、同分散）に替えて採点：
4.44 対 4.46。`flat` も 4.44。**Day 043 の 4.76 対 4.85 という差は、厳密なローブに
対しては消えている。** カーネルの形の議論に入れるほど、楕円の大きさがまだ正しく
ない、という順序だと思う。今日はそれを直した側なので、明日以降もう一度聞く価値が
ある。

## つまずき（記録用）

**旧ハーネスを壊さずに移した。** `cell` / `ripFetch` / `box` / `eigenEllipse` /
`tapRule` を `scripts/rip.mjs` に出し、`aniso-error.mjs` はそれを import する形に
した。2つのハーネスが「ripFetch とは何か」で食い違ったら、今日の議論は決着不能に
なり、しかも**それは結果に見える**。移した後に旧ハーネスを走らせて、Day 043 の表が
**印字された桁まで全部一致**することを確認してから先に進んだ（4.76 / 5.26 / 6.03 /
7.11、bin も9行すべて）。Day 043 が `png.mjs` に `readPng` を移したのと同じ理由の
同じ移動。

**最初の掃引は狭すぎて、答えを間違えかけた。** LTC の伸長を 1〜18 倍で振ったら
構成の 97% が「窓より広い」帯に落ち、支持域の効果が 8.15 → 4.52 と出た。
しかし漆の roughness 0.05 は α = 0.0025 で、LTC 行列はそこを数百倍に引き伸ばす。
1〜256 倍に広げて掃き直したのが上の表。**近景の板が解像している以上、細いローブは
存在していて、掃引がそれを含んでいないなら掃引の方が間違っている。**

**`+ 中心も` を Day 044 の一部として実装しかけた。** 導出が同じなので疑わなかった。
測ってから外した。ハーネスを先に書いたのが効いた唯一の場面。
