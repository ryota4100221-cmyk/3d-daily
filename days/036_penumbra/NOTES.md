# Day 036 — Loop 09 · ランプに大きさがある「Penumbra」（fully deferred lighting / PCSS）★★★★★

## 狙い

Day 035 は自分の NOTES の「次に試したいこと」に、こう書き残した：

> **ライティング全体を遅延へ。** アルベドと radiosity が揃った今、three のマテリアルを
> 捨てて直接光も自前で解けば、直接光・wash・戻り光が同じ単位で語れるようになる。

この1週間、このレンダラで面白いところは全部こちら側にあった——ボリューム、拡散、
wash、戻り光、テンポラルフィルタ。そして**その全部の一番下にある項**、つまり
「面に実際に当たっている光」だけを、ずっと他人（three）が計算していた。

その結果、**1つのランプに対して影マップが2枚**あった。three のもの（投影空間で梱包され、
ライティングマテリアルにだけ配られる）と、こちらのもの（Day 031 で作った、メートル単位の
線形距離）。両者はバイアスの範囲で一致していただけで、厳密には一度も一致していない。

今日は beauty パスを削除し、`DirectionalLight` を削除し、手続き環境マップを削除して、
composite が G-buffer から直接光を自分で解く。**シーン描画が1回減り、影マップが1枚減り、
フレーム内の全項がやっと同じ単位になった。**

そしてそれが今日の絵を買う。**影のテストを自分で持つと、yes/no を聞くのをやめられる。**

## 新しく入れた技法

### 1. 完全なディファードライティング（今日の構造）

composite が G-buffer の albedo・roughness・normal から Lambert + GGX を1ローブ評価する。
`beauty` パスは消えた。35日間ずっとこのファイルには「シーンをマテリアル付きで描いて
three に照らさせる」ステージがあり、下流はその画像を**中身の見えない入力**として扱っていた。

消したことで得られたもの：

| | 昨日まで | 今日 |
|---|---|---|
| シーン描画 | 3回（light depth / G-buffer / beauty） | 2回 |
| 影マップ | 2枚（three のと自前の） | 1枚 |
| radiosity の中身 | 「three の出力 + 自前の wash」 | `direct + wash`（6行離れた場所で計算した2項の和） |
| 環境マップ | 全面に静かな下駄 | **削除** |

G-buffer には roughness が増えた（albedo アタッチメントの alpha、昨日まで 1.0 を運んでいた）。
Day 034 が albedo を足し、Day 035 が radiosity を足したのと**同じ形の変更**が3日続いた——
足りないのはパスではなくチャンネル。

背景の書き割りは G-buffer の **EMISSIVE バリアント**になった。beauty パスが消えたので
グラデーションを評価する場所がなくなったが、そのメッシュは元々 G-buffer に深度と速度を
書きに来ている。そこで評価して albedo に書き、matId で印を付け、composite が
ライティングせずそのまま出す。パスは増えていない。

**環境マップの削除**が一番大きな主張の変更。Day 002 以来ずっと手続き IBL が全ての面の下に
「静かな光の床」として敷いてあり、Day 034 からフィルを1つずつ外してきた。これが最後の1つ。
残ったのは検証可能な主張——**このフレームで、ランプに（何段か隔てて）照らされていないものに
照らされている面は1つもない。**

### 2. Percentage-Closer Soft Shadows（今日の絵）

ランプは点ではない。半角 `θ` を張るので、面から `g` メートル上の遮蔽物は幅 `θ·g` の
半影を落とす。それだけが技法の全部で、使うのに3手：

```
1. BLOCKER SEARCH  描いてよい最大の半影サイズの円で周りを見て、
                   自分より手前にあるタップの距離を平均する → d_b
2. PENUMBRA WIDTH  w = θ · (d_r − d_b)  ← ワールド単位（メートル）
3. PCF             w / (2·halfSize) がそのまま uv 半径。その円で PCF。
```

**手順2が成立するのは、このマップが Day 031 からずっとメートルで書かれているから。**
投影空間に梱包された深度なら、ここで unpack と微分が要るうえ、出てくる数は誰も長さとして
推論できない。5日前に「マーチが面に乗っていない点の素の距離を要る」という**まったく別の
理由**で線形にしたことが、今日そのまま配当になった。

サーチ円内のどのタップも遮蔽していなければ、その点は照らされていて即 return する。
画面の大半がここで抜けるので、この技法が成立している。

**タップは黄金角スパイラル**（保存した Poisson ディスクではない）。同じソースが 1 / 2 / 3 /
4 / 8 / 20 タップで3回コンパイルされるので、どの本数でも均等なのはスパイラルだけ。
回転はピクセルごと（interleaved gradient noise）＋フレームごと。残るのはノイズで、
このレンダラは Day 030 からノイズを食う機械を持っている。

### 3. 同じモデル・同じマップ・3つの予算

これが「Day 031 で three の影マップを読まず自前で書いた」ことの本当の論拠：

| 顧客 | SEARCH | PCF | 支払い方 |
|---|---|---|---|
| 面（composite） | 8 | 20 | 画面ピクセルごと1回。床の階調が絵そのものなので1フレームで解像する |
| 空気（injection） | 4 | 2 | froxel ごと＝**236万回**。1フレームでは目に見えて斑。テンポラルフィルタが積む |
| 塵（motes） | 3 | 1 | 1粒1ピクセル。**7,000粒がそれぞれ別のサンプルを引く**ので、粒の場として平均される |

空気の側が今日いちばん気持ちいい。Day 031 以来すべての光条は `step(d-bias, m)` の
**定規で引いた縁**を持っていた。現実の光条はそうならない——スリットを横切っているのは
幅を持つ光源で、境界は距離とともに広がる階調になる。injection のシャドウ推定を故意に
under-sample して、Day 033 から4タップ推定を積んできたフィルタに渡すだけで、
**光条の縁がフレームをまたいで柔らかくなる**。このパスは他に1行も変えていない。

### 4. receiver plane depth bias（つまずきから生まれた必須項）

一定バイアスでは**絶対に足りない**ことに実装中に気づいた。ブロッカーサーチの円は
1.15m ある。この床は光に対して32度傾いているので、その円の端では光空間の深度が **60cm**
変わる。バイアスは 7cm。つまり**平らな床が自分自身を遮蔽物として報告する**。

正しい対処は「受光面の平面そのものを比較の基準にする」こと。光ビュー空間で面の法線を
`nl` とすると、平面上では `dz = −(nl.x·dx + nl.y·dy)/nl.z`、正射影の1 uv は `2·halfSize`
ワールド単位なので：

```glsl
vec2 shSlope(vec3 nWorld) {
  vec3 nl = mat3(uLightView) * nWorld;
  if (abs(nl.z) < 0.12) return vec2(0.0);   // 光に対して真横の面は諦める
  return clamp((2.0 * uLightHalf) * nl.xy / nl.z, vec2(-45.0), vec2(45.0));
}
```

サーチでも PCF でも、参照深度を `d + dot(slope, offset) - bias` にする。
これが無いと床全面がアクネになり、あっても`slope`を入れ忘れると
「平らな床が自分の影で灰色になる」という、遠目には**それらしく見えてしまう**壊れ方をする。

## つまずき（記録用）

**最初のフレームは真っ白なスープだった。** 直接光が出た嬉しさで露出と散乱をそのままに
していたが、環境マップを消しておきながら `intensity 4.6` / `scatter 2.05` / `exposure 1.52`
は昨日の値で、しかも昨日はその上に beauty の三重の減衰が乗っていた。
**遅延化はトーンの再設計を強制する**——同じ絵に見える保証はどこにもない。
3.05 / 1.35 / 1.22 に落として初めて、この企画のトーンに戻った。

**`?pass=2`（直接光だけ）が構図を決めた。** 合成画では階調が霧に埋もれて何も判断できず、
直接光だけを撮った1枚で「柵の影が根元で鋭く先端で溶ける」が確認でき、同時に
「奥の壁は厳密に真っ黒」（＝zero direct の主張が本物）も確認できた。
**ビルド成功≠描画成功≠合成成功、の次に「合成では見えない項がある」。**

**アパーチャ板の距離が、5日間ずっと何の意味も無いパラメータだった。** 平行光なので板を
ビームに沿って動かしても光条は1ミリも動かない。今日それが**ギャップ＝柔らかさ**になった。
昨日の11ユニットのままだと、幅1.2mの光条の両側に90cmの半影がついて、
3本のスリットが**特徴のない1枚のプールに溶けた**。物理的には正しく、絵としては何もない。
`?pass=9`（ランプを点に戻す）を撮って、ハードでは3本の帯がくっきり出ているのに
ソフトでは消えていることが分かり、板を 4.6 まで下げた。
**ランプに大きさが与えられた瞬間、任意だった数値が意味を持った。**

**構図：水平の梁は文字組みに当たる。** Day 027 の教訓の再来。最初は背景に高さ3.3mの壁を
立てたが、（a）見出しの「Penumbra.」に角が刺さり、（b）霧の in-scatter を受けて明るい
灰色の板になり、画面の明るい面積が倍になって暗さが死んだ。
**壁を捨てて梁＋2本の柱の門にした**ことで、暗い余白が戻り、梁の裏側が
「直接光が厳密にゼロ」の受光面という役目もそのまま引き継いだ。

## 構図・トーン

- 光は1つ。フィルは1つも無く、**今日から環境マップも無い**。
- **柵（staves）が主題**。7本の細い棒が浅い弧に立ち、影は全部カメラ手前・左へ平行に走る。
  根元は髪の毛のような線、先端は手のひら幅の階調——**同じ1つの縁が、1枚の中で両方**。
  一番高い1本（3.30m）は先端で umbra が完全に消える：3.3mのギャップの半影は棒より太い。
- **梁（lintel）はいちばん高い遮蔽物**で、フレームで最も広い柔らかい縁を落とす。
  柵が「手のひらの尺度」で言うことを、梁は「部屋の尺度」で言う。
- 梁の裏・柱の前面はどれも `dot(n, L) < 0`＝**厳密にゼロ**。見えているものは全部 wash。
- 鉢だけが素直に直接光を浴びている。比較対象として残した。
- Day 031 からのルール——**作品が中心に据えている物体（絞りの板）は一度も映らない**——を継続。

## 検証（RUN.md の品質チェックに従って）

- `npm install && npm run build` 成功。
- ヘッドレス（Chromium / SwiftShader / 1600x1000）で実描画を確認。収束前の絵が撮れる
  パイプラインなので **65秒待ってから**撮り、空カンバス閾値は 250KB（正常 1.65MB）。
- `?pass=1` / `?pass=2`（直接光）/ `?pass=7`（wash）/ `?pass=9`（ランプを点に）を撮り比べた。
  - `?pass=2`：奥の梁と柱が**完全に黒**＝直接光ゼロの主張が本物。
  - `?pass=7`：梁の裏・柱の前面にちゃんと wash が乗っている＝昨日までの機能は無傷。
  - `?pass=9`：光条が定規の縁になり、柵の影が全部**1本の線**に潰れる。今日の主張そのもの。

## 次に試したいこと

  まだ点光源のもの。LTC か representative point で GGX を面積化すると、鉢のリムの

  可視率をセルに持たせて時間で積めば、サーチは数フレームに1回で済むはず。

  梁の影の先端はもっと広がってよい。多重解像度（遠いほど粗い解像度でサーチ）で外せる。
