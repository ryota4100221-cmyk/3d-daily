## 分解した装置：見えない半球（the half you stand on）

これは **幾何** でできている。シェーダでもカメラでも入力でもない。

受信機は4つの未知数（x, y, z, と自分の時計のズレ t）を同時に解いている。観測1本は

```
rho_i  =  -u_i . dx  +  c*dt        u_i = 受信機から衛星へ向かう単位ベクトル
```

なので、解き心地は全部 `G`（i 行目が `[-u_ix, -u_iy, -u_iz, 1]`）だけで決まり、
`Q = (GᵀG)⁻¹` の対角が HDOP / VDOP / TDOP になる。
**この式のどこにも「上下」は入っていない。** 入っているのは方向だけ。

それでも垂直は必ず悪い。この問題で対称でないものが1つしか無いからで、それが
**足の下の半分が配信されていない**こと。見える衛星は例外なく `u_z > 0`。

大N極限で、仰角マスク s 以上の球冠に一様なら `E[u_z] = (1+s)/2`、`E[u_z²] = (1+s+s²)/3`。
方位平均が x–z・y–z・x–t・y–t の交差項を全部殺すので、垂直の問題は (z, t) の 2×2 に潰れる。
平らな地平（s = 0）では

```
[ 1/3  -1/2 ]                    [ 12   6 ]
[ -1/2   1  ]  det = 1/12  →  逆 [  6   4 ]        横は Q_xx = 3
```

- **σz / σx = √(12/3) = 2** — 厳密に2倍
- **ρ(高度, 時計) = 6/√48 = √3/2 = 0.86603** — 厳密

全球（s = −1）なら `E[u_z] = 0` でブロックが分離し、同じ式が **1.000 と 0.000** を返す。
**垂直のペナルティは丸ごと地面のせい**で、ハードウェアを1つも触っていない。

原理としては「高度を1m上げる」と「時計が1m分遅れている」が、全部の衛星が上にあるときほとんど
同じ観測残差を作るので、解がこの2つを分離できない、ということ。ρ がそれを直接測っている。

## つまずき

1. **全球の反実仮想で ρ が 0 にならない（−0.27 前後で止まる）。** 最初はバグを疑ったが、これは正しい。
   閉形式の 0.000 は「球に一様」を仮定していて、実在のGPS配置は傾斜55°なので**極を避ける**＝一様ではない。
   24機で地面を外しても、配置そのものが持っている僅かな上下の偏りが残る。
   σz/σx のほうは 1.02 まで戻るので、**主張（地面が原因）は壊れていない**。式の仮定と実物のズレが
   ρ の 0.27 として見えているだけで、これは消さずにそのまま画面に出している。
2. **1回目の実描画で表の数字が全部「—」のまま焼き付いた。** 3Dは出ているのに DOM だけ初期値。
   virtual-time の下では React の setState がスケジュールされても最後の合成に間に合わないことがある
   （Day 050 と同じ穴）。対処は「React state を経由しない」こと — 数値は `useFrame` の中から
   `textContent` に直接書いている。60Hzの再レンダも同時に消えた。
3. **カメラが近すぎてドームが画面から溢れた。** `DOME = 3.25` に対して距離 7.5 では半球が収まらない。
   距離 20.2・fov 30・仰角 43.8° まで引いて、ようやく「空の半分」と「足の下の半分」が同じ絵に入った。
4. **誤差楕円体がドームを食い潰した。** スケール K = 0.62 だと σz が大きい時刻で楕円体が空より大きくなり、
   主題（2つの半球）が消える。K = 0.35 に落として**楕円体をドームの内側に収めた**。
   絵の主役は楕円体ではなく、楕円体をそうしている空のほうなので。
5. **地平線が消えて上下が1個の球に見えた。** 線の色を明るくするだけでは足りず、
   `y=0` に地面の面そのものを入れて初めて「切られている」が読めた。
6. **琥珀の2本（σz の柱と σx の赤道）が地面に塗り潰された。** `renderOrder` と
   `depthTest={false}` で最後に描くようにした。楕円体本体と埋まっている衛星も同じ扱いにしてある。
   **地面より下のものは、見えなくするのではなく暗く見せる** — 問題は「足の下の衛星が無い」ことではなく、
   **在るのに解に使わせてもらえない**ことなので、透けているほうが正しい。
7. **変化ゲートに2回落ちて、絵を作り直した。** ここが今日いちばん時間を使ったところ。
   - 1回目 **0.079**（074_readable に近い／要弁明帯）。2回目、地面を薄い面にして **0.065** と*悪化*。
   - `<!-- SAMEISH -->` を書けば通せたが、**書かなかった**。あの弁明は「動きが主役だから静止画が近い」
     ときのためのもので、今日の近さの理由はそうではない。074 と私の絵は中身は全然違うのに、
     8×8セル＋輝度ヒストグラムから見ると**どちらも「真っ黒な画面の真ん中に明るい塊」**でしかなかった。
     つまりゲートは正しく「構図が同じだ」と言っていた。弁明できない近さは、ただの再演。
   - 直したのは配色ではなく**構図**：地面に本当の明度を与えた。これは絵の都合であると同時に
     主張の都合でもある — この作品は**「地面がやった」と言っている**のに、その地面を虚無で
     描いていたのだから、下手な絵であるだけでなく議論としても弱かった。
   - 結果 **0.206**（最近傍 078_pushbroom）。🔴0件 ⚠️0件。
8. **地面を明るくしたのに真っ黒のままだった（今日いちばん質の悪いバグ）。** `ShaderMaterial` を
   生で書くと、組み込みマテリアルが内部で持っている **linear → sRGB のエンコードが付かない**。
   `THREE.Color('#38465e')` は r169 の ColorManagement でリニア値 (0.038, 0.065, 0.112) に変換され、
   それを `gl_FragColor` にそのまま書くと sRGB バッファへリニア値を流し込むことになり、
   **指定した色よりはるかに暗く出る**（実質 `#040711`）。色を3段明るくしても絵が変わらないので
   最初はレンダ順を疑ったが、原因はこれ。`#include <colorspace_fragment>` を1行足して解決。
   ビルドは当然通るし、警告も出ない。**撮った1枚を目で見るまで分からない類**。
9. **今度は明るすぎて全面が寝てしまった。** エンコードを直した瞬間、同じ色指定が本来の明るさで出て、
   地面が画面いっぱいに広がり DOM の淡いグレーの文字が読めなくなった（`ground: 暗` も嘘になる）。
   半径 17 → 10、フェードを `smoothstep(0.16, 0.74)` に絞って、**ドームの下だけを照らす光だまり**にした。
   文字は暗いままの四隅に置いてある。
10. **shot.mjs の閾値を前日から引き継いでいた。** Day 080 の `SHOT_MIN=300KB` は、
   この日の実描画を**成功しているのに失敗と誤判定**してリトライ階段を登り切っていた。
   しかもこの閾値は絵を作り込むほど動く（実測：初期の疎な版 185〜211KB → 地面を入れた最終版 399KB／
   空カンバスは終始 66KB）。**閾値は前日から引き継がず、その日の空カンバスと実描画を両方測って置く。**
