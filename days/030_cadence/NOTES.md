# Day 030 — Loop 03 · 動き「Cadence」（ループ＆深化 / 動く彫刻）★★★★★

## 狙い

Day 029 の Scene.jsx は、冒頭のコメントで自白していた——
**「ここにあるものは全部わざと静止している。モーションベクタが『世界は固定・カメラだけが動く』
前提だから、形がひとつでも漂った瞬間に履歴が滲む」**。
つまり29日間の静物は、美意識のふりをした**レンダラの制約**だった。

今日はその制約を外し、**動きそのものを主題**にする。
Day 029 の NOTES に自分で書いた「次に試したいこと」のうち
①オブジェクト単位の前フレーム行列（＝静物の縛りを外す）と ④最終画像へのTAA を回収し、
そこから当然出てくる第三の技法として**速度バッファからのモーションブラー**を足した。

止まっている軸が1本、その周りを**4つの速度**で回るもの。同じ1フレームの中に
0.045 rad/s（全体の揺れ）から 4.0 rad/s（バトン）までを同居させ、
「1フレームでは掴めない速さ」を画面に出す。

## 新しく入れた技法（前日までの自分から1段）

### 1. オブジェクト単位／インスタンス単位の前フレーム行列

昨日の頂点シェーダは `vPrev = uPrevViewProj * world`——**前フレームのカメラ1個**が
過去の全部だった。今日は各メッシュが自分の `uPrevModel`（前フレームの matrixWorld）を渡す。

```glsl
vec4 prevLocal = vec4(position, 1.0);
#ifdef PREV_INSTANCE
  prevLocal = aPrevInstance * prevLocal;   // インスタンスごとの過去
#endif
vec4 prevWorld = uPrevModel * prevLocal;   // オブジェクトごとの過去
```

- **`scene.overrideMaterial` は使えない**。あれはシーンに1枚のマテリアルで、
  「前フレームの行列」は per-object の事実だから、**メッシュごとに G-buffer マテリアルを持つ**
  （Map で遅延生成／three はシェーダ文字列が同じならプログラムを共有するので実質タダ）。
- **`aPrevInstance` は itemSize 16 の InstancedBufferAttribute**。そもそも `instanceMatrix`
  自体がこれ（mat4 attribute に16幅のインスタンス属性をバインドし、threeが内部でvec4×4スロットに割る）
  なので、2枚目を足すのは概念的にゼロコスト。GLSL3では prefix の `#define attribute in` が効くので
  `attribute mat4 aPrevInstance;` と書ける。
- 記録は**フレーム末尾で1回**：`e.prev.copy(o.matrixWorld)` と
  `aPrevInstance.array.set(instanceMatrix.array)`。順序は
  ①ポーズ更新 ②カメラ ③G-buffer（過去を読む）…⑥present ⑦過去を書く。
- 副産物：ブレードは「自分の周回 × 自分のツイスト × 上位グループの揺れ」の3つで動くが、
  **どれも前フレームの行列に既に焼かれている**のでシェーダ側は何も知らなくてよい。
  階層アニメーションが自動的に正しくなる。

### 2. TAA（最終画像への時間的アンチエイリアス）＝ MSAAを捨てた

`camera.projectionMatrix` の z 列を毎フレーム **Halton(2,3)** でサブピクセルずらし、
速度バッファで履歴を引き戻して 0.93 混ぜる。8フレームで1ピクセル内8点＝1spp のまま超解像。

**これが Day 029 の負債を返す**：昨日はビューティ4xMSAA・G-buffer 1サンプルで
シルエットが食い違い、水マスクを1pxフェザリングして辻褄を合わせていた。
今日は**ビューティも1サンプル**（`samples: 0`）＝両バッファが構造的に一致し、マスクは素で読める。
アンチエイリアスはTAAの仕事になった。

履歴を**拒否する**仕組みが本質。3つ入れた：

- **深度リジェクト**：履歴のalphaに線形深度を書いておき、`prevUV` の深度が違えば
  ディスオクルージョンとみなして捨てる。
- **分散クリッピング（YCoCg）**：3x3近傍の平均μと標準偏差σから `μ ± 1.15σ` の箱を作り、
  履歴を**μ→履歴の線分に沿って**箱へ押し込む。単純な min/max クランプは外れ値を残すが、
  線分クリップは**速い縁の後ろのゴースト**を消す。今日はそれがバトンなので実務的な話。
  YCoCg で clip するのは、輝度が1軸になるので「明るすぎる履歴」が色相方向に引きずられないため。
- **可逆トーンマップ**（Karis の `c/(1+luma)`）：線形HDRのまま混ぜると1つの高輝度サンプルが
  近傍を支配して消えないファイアフライになる。圧縮空間で混ぜて戻す。

**ジッタは速度に混ぜてはいけない**。`gl_Position` はジッタ付きの行列で描くが、
`vCur`/`vPrev` は**ジッタ抜きの行列**で作る。混ぜると静止ピクセル全部が毎フレーム
半ピクセルの「動き」を報告し、AAが自分の尻尾を追いかける。
逆に、スクリーン空間再構成側（SSR/composite）は**バッファがジッタ済み**なので
`viewRay(uv - uJitter)` でクリーンuvに戻す必要がある。

### 3. 速度バッファからのモーションブラー

素朴に「各ピクセルを自分の速度方向へ伸ばす」と、動く物体は内側だけ柔らかく**縁は剃刀**になる。
隣の静止ピクセルは速度0だから何もぼけないからだ。だから

1. 半径 `uMaxBlur*0.5` のリングを8点サンプルし、**近傍で最大の速度**を採る
   （静止ピクセルにも「どちらから滲みが来るか」を知らせる）
2. その方向に23点ギャザー
3. 各タップを **reach テスト**で重み付け：`reach = 0.5*max(|v_tap|, |v_center|)` に対し
   `need = |offset|` が届かないタップは落とす。これが**背景まで一緒にぼけるのを防ぐ**唯一の仕掛け。

シャッターは**長さではなく時間**。速度バッファは uv/**フレーム**なので `shutter/dt` を掛ける。
1/30秒のシャッターは30fpsでも144fpsでも同じ長さに写る＝機械の都合ではなく「絵」になる。

### 4. 2つの時計は交換できない（今日いちばん効いた設計判断）

- **リビール（一回性の演出）は壁時計**。Day 028 で `min(delta)` 累積のワイプを書いて
  実質フレームカウンタになり、遅いマシンで永遠に終わらなかった教訓そのまま。
- **彫刻は「クランプした delta の累積」**——逆の選択を、逆の理由で。
  速度バッファは2ポーズ間の**弦**であって弧ではない。1フレームに1秒かかるとバトンは230°回り、
  その弦は速度について何も語らない。ステップを 1/30 秒で頭打ちにすれば、
  遅いマシンは**間違った絵ではなくスローモーション**を見せる。
  そして blur は同じ dt でスケールされるので、常にシャッター1本分ぴったりになる。

### 5. 部屋の関数が2次元になった（palette.js）

Day 029 は `skyAtHeight(y)`——水平な帯。水平な鏡はそれを別の水平な帯にするだけ。
今日は `skyAt(x, y)` にして**垂直なライトスロット**を置いた。水平な鏡が
垂直なスロットを映すと**手前へ走る一筋**になる。黒漆の板が「磨かれている」と読めるのは
これだけが理由で、背景メッシュと反射パスは相変わらず同じ1つの定義を共有している。

### 6. 反射の履歴を「映っているもの」の速度で手放す

板は静止しているので、板自身の速度で履歴を戻すのは**厳密に正しく、映っているものには完全に間違い**。
鏡面の表面と鏡面の像は違う速さで動く——Day 029 の NOTES が未解決として残した問題。
今日の答えは、正しい再投影の代わりに**hit点の速度で feedback を手放す**：

```glsl
float blend = uBlend * (1.0 - clamp(hitVel * 0.16, 0.0, 0.92));
```

部屋の静かな隅は積分してグロスに収束し、振り回されるバトンは毎フレーム描き直されるので尾を引かない。
安い解だが両端で正しく振る舞う。厳密解（hit点の深度で速度を作り直す）は宿題に残す。

## 造形の話（レンダリングでは直せないこと）

- **旋盤の輪郭は「スプライン」と「素のポリライン」を使い分ける**。Day 028/029 は全部
  `SplineCurve` に通していたが、細い軸に付いた台座を平滑化すると
  **日向に置き忘れたロウソク**になる。建築的な形は制御点そのものを輪郭にする（`lathePoly`）。
  投げた形（pebble / bud）だけスプライン。
- **リングは「リム」がないとリングにならない**。14枚のブレードを円環に置いただけでは、
  自分の平面に近い視点からは**バラバラの紙片が違う高さに浮いている**だけ。
  厚さ11mmのフープを1本入れると楕円が立ち上がり、ブレードは「それに付いている物」として読める。
  そのうえで 0.26 rad 傾けて楕円を開く（傾けると速度バッファに垂直成分も出る）。
- **高さを4段に分ける**。反対回りのアームが同じ平面にいると互いを貫通する。レンダリングでは直らない。
- **部屋を暗くするまで板は水にも漆にも見えなかった**。初版は露光1.5＋明るい空で、
  磨かれた板ではなく**青いプール**になった。Day 029 の「水は暗いから水ではなく、暗い空を映すから暗い」
  がそのまま効いた。
- リムの `position.y` を忘れると、**フープだけ板の上に落ちる**（インスタンスは行列に高さを持つが、
  素のメッシュは持たない）。実描画を見るまで気づかない類のバグ。

## ハマった点（次の自分への申し送り）

- **`uVelScale` のクランプが上限8で、そこに張り付いていた**。ヘッドレス（`--virtual-time-budget`）では
  R3F の `delta` がほぼ0になるため `shutter/dt` が上限に飽和し、
  **シャッターを4.6倍にしても絵が1ピクセルも変わらない**という診断しづらい症状になった。
  「効かないときはまずクランプを疑う」。対処は dt を**両端でクランプ**（1/600〜1/30）して
  velScale 側のクランプを外すこと。上限と下限は同じ量を守っている。
- **空カンバスの閾値はケチると意味がない**。RUN.md 通りバイト数リトライを入れたが、
  閾値を 60KB にしていたので **76KB の完全な空フレーム（DOMだけ残る）を「OK」と誤判定**した。
  1600x1000 のこの作品は正常時 1.4MB。**閾値は正常値の1/4程度**に置く。
- **この環境の ffmpeg には PNG デコーダが入っていない**。拡大して縁を確認したいときは
  ブラウザに `drawImage` で切り出させて撮り直すのが早い（`zoom.html` 方式）。
  ビルド成功≠描画成功の次に「全体図≠品質確認」がある。ブラーもAAも**等倍では判定できない**。
- ヘッドレスは delta≈0 なので**シーンは実質止まる**。だから構図は撮影のたびに変わるのではなく
  `?phase=` で選ぶものになった。遅いオービットの作品では**どの瞬間を撮るかが設計**。

## デバッグ用URLパラメータ（Day 023 `?grade` / 025 `?t` / 027 `?speed` の系譜）

- `?t=12.5` — シーン時刻をピン留め。速度が全部0になるのでTAAは完全に澄んだ静止画へ収束するが、
  **動きが消えるのでブラーも必然的に消える**。バッファを読むには正しく、ブラーの判定には不適。
- `?phase=8` — 止めずに8秒目から始める。構図を選ぶため。
- `?pass=4` — キーボードなしでパスを切り替える。**ヘッドレスが「速度バッファに本当に主張通りのものが
  入っているか」を確認できる唯一の手段**。実際これで、バトンの2つのビーズが
  逆向き（teal と salmon）に出ていることを確認した＝回転体の per-pixel 速度が正しい証拠。

1–6キー / クリックで Composite / Beauty(1サンプル) / Normals / Velocity / Reflection / TAA off。
**TAA off は今日の主張のA/B**そのものなので入れた（縁が階段状に崩れる）。
