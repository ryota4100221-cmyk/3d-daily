## 何を再現したか

キー演出を1つに絞る。「FVがcanvas」で「地が #0f0f0f」で「ブランド色を1つも置かない」
監視会社のトップに映っているのは、**機上センサが吐いている画像そのもの**である。
ならば再現すべきは色でも文字組みでもなく、**その画像がどうやって出来ているか**のほうだ。

これは 幾何でもシェーダでもなく **時間** でできている。

航空ラインスキャナ（pushbroom）は画素の行を**1本しか持たない**。
だから、どの瞬間にも絵が存在しない。絵が出るのは機体が動くからで、
画像の n 行目は「時刻 n の世界」である。

**→ 画像の縦軸は、空間ではなく秒になる。**

`rig.js` の断面はこの2行しかない：

```glsl
float age = (1.0 - q.y) * uSpan;   // 画素の縦位置 = さかのぼる秒数
float xg  = uS - uGS * age;        // その行の地上位置（行の中では定数）
```

`xg` が `q.x` に依存していないのが全部である。**1つの行のすべての画素は同じ瞬間の世界で、
隣の行は別の瞬間の世界。** フレームカメラには絶対に書けない2行で、ここから下は全部その帰結。

## 分解した装置：時計になった軸

真の長さ **L** の物体は、機体とのすれ違い速度 **|V − v|** で通り過ぎるので
**L/|V−v| 秒ぶんの行**を占める。静止物は L/V 秒ぶん。つまり画像上の長さの比は

```
伸び率 k = V / |V − v|
```

に**しかならない**。物体の形にも、大きさにも、距離にも、センサの分解能にも、
ライン周期にも依らない。効いているのは機体との速度差ひとつだけ。

| | 実速度 | 実寸 | 画像上 | k |
|---|---|---|---|---|
| V-01 | 0 km/h（停車） | 4.6 m | 4.6 m | ×1.00 |
| V-02 | 68 km/h | 4.8 m | 11.2 m | ×2.34 |
| V-03 | −92 km/h（対向） | 12.4 m | 7.0 m | **×0.56（前後が裏返る）** |
| V-04 | 113 km/h | 5.1 m | 105.2 m | ×20.62 |
| V-05 | **119 km/h（= 機体の対地速度）** | 5.6 m | **∞** | — |

V-05 が画面を上から下まで貫く1本の線になっているのは、線を引いたからではない。
分母 |V − v| が 0 なので、**一度スワスに入った車が二度と出ていかない**からである。
`rig.js` で V-05 だけを特別扱いしている行は無い（`o` の折り返し幅 |V−v|·SPAN + len が
V-05のときだけ len に縮む、というのが全部）。

ドラッグで対地速度 GS を 12〜60 m/s で動かせる。∞ になる車が入れ替わり、
同時に **帯の縦の実長（秒×GS）が変わって地形だけが縦に伸縮する**
——縦軸が時間である以上、速度を変えれば縮尺が変わるのは横軸ではなく縦軸のほうになる。

副産物として出てくるもの（どれも「描いて」いない）：

- **ロールの横揺れ** — 機体のロールは ±1.11° しか振れないが、行ごとに独立に効くので
  直線の道が帯の中で横に蛇行する。フレームカメラなら画面全体が傾くだけで、
  被写体が**うねる**ことは絶対に起きない。
- **起伏による横ずれ**（relief displacement） — 地上点は z = (h − H)·tanθ にあるので、
  尾根は直下点から外へ押し出される。直下（θ=0）ではきっかり 0。
- **列ごとの固定パターンノイズ** — 縦縞。検出器が1列に並んでいて各素子の利得が違うため、
  縞は必ず「縦」に出る。行方向に出ることはない。

## 何を捨てたか

- サイト全体（FV の canvas 1枚だけ。理念セクションもスクロールリビールも作らない）
- **光源**。このシーンには照明が1つも無い。映っているのは全部その面の自己放射（熱）で、
  起伏が見えるのは照らされているからではなく、**夜間の接地逆転で谷に冷気が溜まり
  尾根が暖かい**から。夜の熱画像でエンジン以外にいちばん明るいのは川（水の熱容量）。
- コピーの文言・ロゴ・ナビ。借りたのは**組み方**だけ（等幅1本・全大文字・字間を開ける・
  階層は太さではなく不透明度で作る・有彩色は3つしか使わない・ブランド色を置かない）。
  Geist はこの環境から取れないので system の等幅スタックで組んだ。
- 実写・PBR・環境マップ・ポストプロセス。`engine/` からは1ファイルも持ってきていない。

## つまずき

1. **道と川が重なっていて、道が1枚も映っていなかった。** 初版は
   `roadZ = −118 + 34·sin(x/430)`、`riverZ = 92·sin(x/690) + …` で、両者のレンジが
   ちょうど噛み合っていた。水は `mix(T, water, …)` で道を上書きするので、画面には
   「白い帯と、その上を走る1本の黄色い線」しか出ない。**その黄色い線が V-05 だった**
   ので、装置は最初から動いていたのに「道の中央線」に見えていた。
   直下点をはさんで反対側（川 −70、道 +49）に置き直して両方出た。
2. **車が5台のうち1台しか映らない。** `o`（機体からの along-track オフセット）を
   ±900 m で折り返していたが、その車が帯に映っていられる `o` の幅は
   |V−v|·SPAN + len しかない。V-04 は 27 m ＝ 1800 m 中の 1.5% で、
   ほぼ永久に画面外だった。**折り返し幅を可視域そのものにする**（＝道の上に同じ間隔で
   同じ車が並んでいるのと同じことにする）と、どの瞬間も1台ずつ必ず入る。
3. **速度が嘘だった。** 最初は機体を 92.6 m/s（180 kt）にしたので、∞ になる車が
   333 km/h になった。車で成立しない数字を出した時点で装置の話が入らないので、
   機体を低速の監視UAV（33.0 m/s = 118.8 km/h）に振り直した。
   ∞ の相手が**高速道路の実速度**になって初めて、この表は読める。
4. **地形が雲にしか見えない。** 起伏を素の fbm で、しかもスワス幅に対して
   基本波長が長すぎる（帯の中に 2.3 周期）と、夜の熱画像では稜線が立たない。
   ridged fbm（`1 − |2n − 1|`）にして基本波長を帯の 1/5 まで詰め、
   さらに 12.5 m の細かい粒を足して、ようやく「上から見た山」になった。
